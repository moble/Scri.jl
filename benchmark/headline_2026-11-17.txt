# The headline benchmark (2026-11-17): time and peak memory for 20000 time samples
# Apple M2 Max, 96 GB, Julia 1.13.4
# branch: bms2 at 29e0866; Chairmarks 1.3.1; OhMyThreads 0.8.9; Quaternionic 5.0.0; SphericalFunctions 3.0.0
# main: at 74961f4; Chairmarks 1.3.1; OhMyThreads 0.8.9; Quaternionic 4.5.0; SphericalFunctions 2.2.9
# Python scri: Python 3.14.10; scri 2024.0.14; numpy 2.5.5; numba 0.68.1, with 12 threads for numba
# Julia's threads: 8,1; BLAS threads, which keep their default: 8 with 8, 8 with 1
# Each case ran in a process of its own, one after another, in 132.9 minutes.
# Load average before the first case: 2.4
# Each time is the least of several, in seconds, measured by Chairmarks.

In the headings, `main/8` is `main` with 8 Julia threads, `branch/1` is the
branch with 1 thread, which is what Julia starts with by default, and so on.
`plan` is the branch with a `TransformPlan`.  P is the number of parameters.
A time marked ~ was not measured: it is the number of evaluations times the
time of one, because the gradient would have taken longer than the limit of
600 s.  Memory is the peak resident set size of the process just after
its first call at full size, in gigabytes (2³⁰ bytes); it includes Julia or
Python itself, the compiled code, and the data.

The objective's plan is made with `ℓ_fit`, which costs one more pass over the
pixels than a plan that compares every mode, even when `ℓ_fit` is the data's band
limit.  So these gradients take longer than those of `benchmark/comparison`.
