Scri.BMS — Type
BMS{T<:Real,A,I}

An element of the BMS group: a supertranslation α followed by a (proper orthochronous) Lorentz transformation with frame rotor Λ. We write elements as pairs

\[(Λ, α) = (1, α)\,(Λ, 0),\]

where a product is written in the order in which its factors are applied, Λ ∈ Spin⁺(3,1) is represented by a Lorentz rotor, and the supertranslation is a real-valued function on the sphere, stored as its spin-weight-0 spherical-harmonic mode weights. The second factor is read in the frame that the first produces, so Λ acts about the new origin set by the supertranslation rather than the original one; in the time law t′ = κ(t - A α) below, κ multiplies the shifted time.

The second type parameter A ∈ {+1, -1} is the supertranslation-sign convention: the element acts as t′ = κ(t - A α). This says how the element's own stored α is read as a time shift, so it is fixed at construction (default +1, set with the c_α keyword). Because A factors out of the group law, an element (Λ, α) with A = -1 is the same transformation as (Λ, -α) with A = +1.

The third type parameter I ∈ {+1, -1} is the null-infinity representation: it records which labeling of the celestial sphere the stored α modes refer to — the outgoing labeling of $ℐ⁺$ (I = +1, the default) or the antipodal past-light-cone labeling of $ℐ⁻$ (I = -1; set with the ℐ keyword). The groups $BMS⁺$ and $BMS⁻$ are isomorphic under the antipodal matching, so this is purely a choice of representation: the element (Λ, α) with I = -1 is the same abstract transformation as (Λ, α∘A) with I = +1, where A is the antipodal map — (-1)^ℓ on each mode. See the conversion constructor BMS(g; c_α, ℐ) below, and Representations of the supertranslation.

Both conventions are pure bookkeeping. Operations combining two elements (compose, ==, isapprox) accept any mix: the differences are accounted for exactly, and wherever the two inputs disagree the result uses the default (+1) convention. Data must be given on a fixed portion of null infinity, so DataComponents includes ℐ as a type parameter; the transform! bridge re-represents the element to match the data. See the conventions page.

See the BMS group documentation for details about the group structure, action, and conventions.

The element acts (passively) on a point (t, 𝐤) of ℐ as t′ = κ(𝐤)(t - c_α α(𝐤)), with the new direction read from Λ̃𝐤Λ. The functor g(t′, k̂′) maps new coordinates back to old ones, and new_coordinates(g, t, k̂) maps old ones to new; see also conformal_factor and the group law.

Storage

  • Λ::Lorentz{T}: the frame rotor $Λ = B(v⃗)\,R$, which takes the old legs to the new ones, $𝐞'_μ = Λ\,𝐞_μ\,Λ̃$. Its reverse $Λ̃$ gives the new components of a fixed vector, $V^{μ'} = (Λ̃\,𝐕\,Λ)^μ$, and so the new coordinates of a fixed event; see Frames and Components. Note that ±Λ represent the same transformation (the double cover); ==, isapprox, and hash account for this.
  • α::Vector{Complex{T}}: mode weights of the supertranslation, of length (ℓₘₐₓ+1)², ordered by increasing ℓ ∈ 0:ℓₘₐₓ, then increasing m ∈ -ℓ:ℓ — that is, the mode (ℓ, m) is stored at index ℓ² + ℓ + m + 1. The constructor enforces the reality condition α_{ℓ,-m} = (-1)^m ᾱ_{ℓ,m} (via impose_reality), so that the function on the sphere is real-valued.

Constructors

BMS(Λ, α)             # frame rotor (a Lorentz, or a Rotor for a pure rotation) and modes
BMS{T}(; kwargs...)   # assemble from parts; see below
BMS(g; c_α, ℐ)        # convert an element between representations; see its own docstring

The positional form stores its Lorentz part exactly as given, as the frame rotor, so BMS(R, α) and BMS{T}(; frame_rotation=R, supertranslation=α) have the same Lorentz part, with the meaning that R has in transform!.

The keyword constructor accepts any combination of

  • supertranslation: mode weights as above (any perfect-square length);
  • frame_rotation: a Rotor, or anything that rotor_argument reads as one: a Quaternion, which is normalized, four components (w, x, y, z), which are normalized, or three components, which are a rotation vector;
  • boost_velocity: a QuatVec, 3-vector, or 3-tuple with |v⃗| < 1;
  • time_translation: a real δt;
  • space_translation: a QuatVec, 3-vector, or 3-tuple δx⃗;
  • c_α, ℐ: the conventions described above (both default +1);
  • ℓₘₐₓ: the resolution of the stored α (defaults to the smallest that fits).

The internal representations are Vector{Complex{T}}, Rotor{T}, and QuatVec{T}, but any input convertible to those is accepted — real or lower-precision mode vectors, plain 3-vectors for velocities and translations, and so on; the float type T is promoted to accommodate all the parts. A part of any other kind throws an ArgumentError.

The keyword constructor stores the frame rotor Λ = Boost(v⃗) * Lorentz(R), which rotates the legs by R and then boosts them with velocity v⃗, both given in the old frame's components, so that frame_rotation and boost_velocity return exactly the R and v⃗ arguments of transform!. In particular κ(𝐤) = 1/(γ(1 - ℐ v⃗⋅k̂)) for a pure boost, where ℐ is the element's representation I. The translation parts contribute α(k̂) = c_α(δt - ℐ δx⃗⋅k̂) in the labeling selected by ℐ — i.e., the supertranslation of the spacetime translation of the origin by the 4-vector (δt, δx⃗), which is the same physical translation in every convention. Because the supertranslation is applied first, the new origin is the event whose old coordinates are (δt, δx⃗), whatever v⃗ and R are. If supertranslation is also supplied, any time_translation and/or space_translation content is added to it to produce the total supertranslation.

Operations

Group composition via * (or ∘, or compose with explicit band limits) is written in the order of application: g₁ * g₂ applies g₁ first, and then g₂, whose parameters are read in the frame that g₁ produces, so that lorentz(g₁ * g₂) == lorentz(g₁) * lorentz(g₂). The inverse is inv, and the identity one. Applied to a point of null infinity, g(t′, k̂′) returns the old coordinates of the point whose new coordinates are (t′, k̂′), so that (g₁ * g₂)(t′, k̂′) ≈ g₁(g₂(t′, k̂′)...). Accessors: ℓₘₐₓ, lorentz, supertranslation, frame_rotation, boost_velocity, translation, time_translation, space_translation, proper_supertranslation.

Scri.BMS — Method
BMS(g::BMS; c_α=+1, ℐ=+1)
BMS{T,A,I}(g::BMS)

The same abstract BMS transformation as g, re-expressed with the requested conventions (and, in the fully parameterized form, float type).

Changing c_α negates the stored modes (t′ = κ(t - c_αα) is unchanged under (c_α, α) ↦ (-c_α, -α)). Changing ℐ relabels the sphere by the antipodal map A — the antipodal matching that identifies $BMS⁺$ and $BMS⁻$ — so the modes transform as α ↦ α∘A, which is (-1)^ℓ on each ℓ block, since Yₗₘ(-k̂) = (-1)^ℓ Yₗₘ(k̂). The Lorentz part is unchanged in both cases. Both operations are exact (pure sign flips) and involutive. See Representations of the supertranslation.

Note the distinction from constructing an element with non-default conventions from raw parts: BMS(Λ, α; ℐ=-1) attaches the ℐ⁻ meaning to the raw modes α, whereas BMS(BMS(Λ, α); ℐ=-1) converts the ℐ⁺ element (Λ, α) into its matched ℐ⁻ form — a different element unless α has no odd-ℓ content.

Scri.BMS — Method
(g::BMS)(t′, k̂′) -> (t, k̂)

Return the old coordinates of the point of ℐ whose new coordinates under g = (Λ, α) are the time t′ and the (unit) direction k̂′. The new components of a fixed ray are those of $Λ̃\,𝐤\,Λ$, so the old ray is $𝐤 ∝ Λ\,𝐤'\,Λ̃$, and inverting the time law $t' = κ(𝐤)\,\left(t - c_α\,α(𝐤)\right)$ gives

\[t = \frac{t'}{κ(𝐤)} + c_α\,α(𝐤), \qquad 𝐤 ∝ Λ\,𝐤'\,Λ̃,\]

with κ as in transform_ray. This is the map that transform! evaluates at every new pixel and time, and it composes like a function: (g₁ * g₂)(t′, k̂′) ≈ g₁(g₂(t′, k̂′)...), which is why ∘ is a synonym for *. The other direction is new_coordinates(g, t, k̂), which is exact; inv(g)(t, k̂) agrees with it only up to the band limit of inv, which truncates the supertranslation of a boosted element.

Both conventions are the element's own type parameters, fixed at construction: the supertranslation sign c_α says how α enters the time shift, and the null-infinity representation ℐ says which $ℐ$ — and which labeling of it — the coordinates refer to. To act on the other $ℐ$, convert the element first with the conversion constructor BMS(g; ℐ=…).

Scri.Conventions — Type
Conventions{S,R,L,M,Ψ,Σ,Λ,H,N,Φ,Ð,A}

Sign and scale factors setting conventions. The parameters are

  • c_s for the signature of the metric
  • c_R for the Riemann tensor
  • c_l for the tetrad vector l
  • c_m for the tetrad vector m
  • c_ψ for the Weyl components
  • c_σ for the shear
  • c_λ for the "incoming" shear
  • c_h for the complex strain
  • c_N for the News, $N = c_N ∂ᵤh$
  • c_φ for the Faraday components
  • c_ð for the ð operator
  • c_α for the supertranslation law

For precise definitions of each of these factors, their allowed values, and the structural conventions this package fixes once and for all (e.g., $l$ outgoing, $m$'s handedness, $h$ of spin weight $-2$), see the documentation. The default values are all 1, corresponding to the SXS conventions. The constructor validates the values: c_s, c_R, and c_α must be $±1$; c_l must be real; c_m must have unit modulus; and every factor must be nonzero.

Internally, the code always computes $ð$ with the Newman–Penrose normalization, $c_ð = 1$, so the value of c_ð doesn't currently affect any result. It is recorded so that a Conventions describes a convention completely, and so that formulas in the documentation can be compared with formulas written in that convention. So that this is not missed, the keyword constructor warns whenever c_ð ≠ 1, though the named presets do not issue any warning about it.

The types of all of these factors are retained as the type parameters of Conventions listed above — S,R,L,M,Ψ,Σ,Λ,H,N,Φ,Ð,A — to allow for type stability and compile-time optimization. Most common conventions — or those that only use ±1 — will compile away entirely.

Construct with keywords (validated), or by name from the named presets:

Conventions()                   # SXS defaults
Conventions(; c_s=-1, c_l=-√2)  # a custom convention
Conventions(:MB)                # a named preset; see the symbol-argument docstring

Scri.Conventions — Method
Conventions(name::Symbol; T=Float64)

Named presets. Available: :SXS (the package default), :MB (Moreschi/Boyle), and two for the Python package scri in its versions 2024.x: :scri2024abd for its AsymptoticBondiData and :scri2024wm for its WaveformModes. T sets the type of every value other than $±1$, such as √2 and 1/2; the signs are stored exactly regardless. Values that are not clear from the references are left at the default.

The :MB preset follows Boyle [7] exactly. (Equation numbers here refer to the arXiv version of that paper.) Its tetrad has $c_s = -1$, $c_l = \sqrt{2}$, and $c_m = -1$, as explained in a footnote of the "Tetrad" page; the mixing of the Weyl components in Eqs. (17) confirms the product $c_l c_m = -\sqrt{2}$. The paper's $ð$ is that of Geroch, Held, and Penrose, which is $1/\sqrt{2}$ times the one used here, so $c_ð = 1/\sqrt{2}$. Its time law $u' = k(u - α)$ (Eq. 8a) has the same sign as ours, so $c_α = 1$. The paper defines the shear in spinor form as $σ = o^A o^B ῑ^{B'} ∇_{BB'} o_A$ (Eq. 18). In the paper's $+---$ signature, where $g_{ab} = ε_{AB} ε̄_{A'B'}$ and $l_a = o_A ō_{A'}$, this is $σ = m^a m^b ∇_b l_a$, which gives $c_σ = -1$ and $σ^{[MB]} = \tfrac{1}{2} h̄^{[SXS]}$, as the supertranslation law of Eq. (19) confirms. The relation $ψ₄ = -∂²ᵤσ̄$ (Eq. 20) then fixes the product $c_s c_ψ c_R = 1$, which gives $ψₙ^{[MB]} = (-\sqrt{2})^{2-n} ψₙ^{[SXS]}$ and makes the Schwarzschild $ψ₂$ equal to $-M$, as in the SXS convention. The paper fixes no sign of the Riemann tensor, and the split of that product between $c_ψ$ and $c_R$ affects no result; we record $c_ψ = -1$ and $c_R = 1$. The paper defines the strain by $h = σ̄$, so $c_h = -1/2$, negative because the metric perturbation itself changes sign with the signature. The paper calls this the commonly used strain, but with its own normalization of $σ$ it is half the usual $h₊ - i h_×$; we follow the equation. Finally, the paper's news is $n = -∂ᵤσ̄$ (Eq. 22), which is minus the time derivative of this strain, so $c_N = -1$. The paper defines no fields on $ℐ⁻$ and no Faraday components, so $c_λ$ and $c_φ$ keep their defaults. The convention table of Iozzo et al. [4] lists the opposite sign for the Weyl components and the strain of this convention. That contradicts the paper, in which Eqs. (18) and (20) fix the sign of the Weyl components, so that the Schwarzschild $ψ₂$ is $-M$, and $h = σ̄$ fixes the sign of the strain. It would also contradict the mass aspect $-\mathrm{Re}\, ψ₂$ of scri.

The Python package scri stores $σ$ and the $ψₙ$ of its AsymptoticBondiData in this convention, but its strain and News are not this convention's; see :scri2024abd below.

The presets :scri2024abd and :scri2024wm describe the data of the Python package scri in its versions 2024.x (checked against version 2024.0.12); a later version of scri is expected to change these conventions. scri uses two conventions side by side, one for each kind of object, so a preset is chosen by the kind of object the data come from.

The :scri2024abd preset describes an AsymptoticBondiData. It differs from :MB only in the strain and the News. The sigma and psi0 through psi4 of an AsymptoticBondiData are exactly those of :MB, but its strain h is $2σ̄$, which is the usual $h₊ - i h_×$, so $c_h = -1$. scri has no News of its own for an AsymptoticBondiData; where it needs one internally, it forms $2∂ᵤσ̄$ with data type hdot, the time derivative of its strain, so $c_N = 1$. In this convention, then, $ψ₄ = -\tfrac{1}{2} ḧ$. The preset applies to the fields of an AsymptoticBondiData, to its strain h, and to the time derivative of that strain.

The :scri2024wm preset describes a WaveformModes. Its strain, News (data types h, hdot, and news), and Weyl components — including any read from an SXS file — are in the SXS convention, and scri transforms them with the SXS laws. The exception is the data type sigma, which holds the shear of an AsymptoticBondiData, $σ = \tfrac{1}{2} h̄ = \sqrt{2} σ^{[SXS]}$, and which scri shifts by $ð_{\mathrm{GHP}}^2 α = \tfrac{1}{2} ð^2 α$. With the SXS tetrad, both are reproduced by $c_σ = \sqrt{2}$, so this preset is the SXS convention with that one change.

Data that scri reads with create_abd_from_h5(..., convention="Moreschi-Boyle") are taken to have the strain $σ̄$, and so are in the :MB convention.

Scri.DataComponents — Type
DataComponents{C, ℐ, V}

Encodes a fixed set of waveform data components at the type level. C is an NTuple{N,Symbol} whose elements are drawn from ValidDataComponents:

(:ψ₀, :ψ₁, :ψ₂, :ψ₃, :ψ₄, :σ, :λ, :h, :News, :φ₀, :φ₁, :φ₂)

The parameter ℐ is the sign of the time direction for which these components are defined: +1 for $ℐ⁺$ (outgoing) and -1 for $ℐ⁻$ (incoming). The default value is +1, since most applications will be for $ℐ⁺$.

The conventions field (of type V<:Conventions) records which convention the component data are expressed in; it defaults to Conventions(), the package-native SXS conventions. The conventions travel with the data descriptor — transform! applies the transformation laws native to that convention, and represent! converts data between conventions.

The inputs may alternatively be strings; any reasonable spelling will be parsed into the canonical symbol form. For example, DataComponents("Psi_3", "psi4", "sigma") will be parsed into DataComponents(:ψ₃, :ψ₄, :σ). The constructor will throw an error if the input components are invalid.

Examples:

DataComponents(:ψ₄)                                    # gravitational waves only
DataComponents(:ψ₄, :ψ₃, :ψ₂)                          # top three Weyl components
DataComponents(:ψ₀, :ψ₁, :ψ₂, :ψ₃, :ψ₄, :σ)            # full Weyl set with shear (ℐ⁺)
DataComponents(:ψ₀, :ψ₁, :ψ₂, :ψ₃, :ψ₄, :λ; ℐ=-1)      # full Weyl set with shear (ℐ⁻)
DataComponents(:φ₀, :φ₁, :φ₂)                          # Faraday components
DataComponents(:φ₀, :φ₁, :φ₂; ℐ=-1)                    # Faraday components on ℐ⁻
DataComponents(:ψ₄, :h; conventions=Conventions(:MB))  # data in the MB convention
DataComponents(:σ, :ψ₄; conventions=Conventions(:scri2024abd))  # scri's Bondi data
DataComponents(:h, :ψ₄; conventions=Conventions(:scri2024wm))  # scri's WaveformModes

Scri.ObjectivePlan — Type
ObjectivePlan(target, t, dc, t′; grid, weights, time_weights, component_weights,
              normalize=false, ℓ_fit=nothing)

Everything about the objective of transform_objective that does not depend on the BMS parameters, computed once and reused at every evaluation:

\[Φ = \frac{1}{𝒩} ∑_j w_j ∑_i v_i ∑_k u_k \left| μ^{ki}_{j} - c^{ki}_{j} \right|^2,\]

where $μ^{ki}_{j}$ is the transformed waveform at pixel j, output time t′[i], and component k, and $c^{ki}_{j}$ is the target there. The notation is that of the page The gradient of the objective.

The arguments target, t, and dc are the target waveform's mode weights, its time samples, and its DataComponents, as for transform!; t′ is the fixed output grid on which the transformed data are compared with the target. Use compute_t′(t, β, δt) to build a grid valid for every transformation an optimizer may try. It may have any length ≥ 1.

The keywords are:

  • grid: a pair (R′ₚ, w) of rotors and sphere weights $w_j$. The default is sphere_quadrature(ℓₘₐₓ), at the target's band limit, which makes the sum over pixels an exact integral over the sphere when the transformed data $μ$ are band-limited to that $ℓₘₐₓ$ too, so that $Φ$ is then exactly the $L²$ norm. A boosted field is not band-limited, so in general the sum is a spectrally accurate approximation of that norm rather than an exact one; a finer grid, such as sphere_quadrature(L) with a larger L, can be passed to reduce the error. With the default grid, data of a higher band limit than the target's are rejected, because the quadrature would not be exact even for them; zero-pad the target's modes to the data's band limit first.

  • weights: per-pixel factors multiplying $w_j$, for example to down-weight a region of the sphere. The default is one.

  • time_weights: the $v_i$. The default is the trapezoid rule on t′, so that the sum over time is an integral even on a non-uniform grid; a single time has weight 1.

  • component_weights: the $u_k$, one per component of dc. The default is one.

  • normalize: if true, $𝒩$ is the same sum with $μ$ set to zero, so that $Φ$ is relative to the target's norm; otherwise $𝒩 = 1$.

  • ℓ_fit: if given, compare only the modes with $ℓ ≤ ℓ_\mathrm{fit}$ of the difference. This leaves out the modes that the data and the target were padded with to make room for the transformation, and any high-$ℓ$ noise in either:

    \[Φ = \frac{1}{𝒩} ∑_i v_i ∑_k u_k ∑_{ℓm:\, |s_k| ≤ ℓ ≤ ℓ_\mathrm{fit}} \left| Π^{ki}{}_{ℓm} \right|^2, \qquad Π^{ki}{}_{ℓm} = ∑_j w_j\, \overline{{}_{s_k}Y'^{ℓm}_{j}} \left( μ^{ki}_{j} - c^{ki}_{j} \right),\]

    where ${}_{s}Y'^{ℓm}_{j}$ is the harmonic evaluated at pixel j of the grid.

    The projection is the quadrature's, so with the default grid it is exact when $μ$ is band-limited to $2ℓₘₐₓ - ℓ_\mathrm{fit}$; ℓ_fit must then be at most the target's band limit. It must be at least the largest $|s|$ among the components. The projection takes one more pass over the pixels, so the objective and its gradient cost about 1.3 to 1.4 times as much with ℓ_fit as without it.

All weights must be finite and nonnegative. The target's pixel values are computed with pixel_waveform on the grid.

Scri.TransformPlan — Type
TransformPlan(ℓₘₐₓ, dc, T=Float64)
TransformPlan(data, dc)

The part of transform! that depends on no BMS parameter, computed once for reuse across calls: the grid transform_grid(ℓₘₐₓ, T) on which the transformed data are analyzed back into modes, and the factorization of the analysis matrix on that grid for each spin weight among the components of dc.

Scri.compose — Method
compose(g₁, g₂; ℓₘₐₓ, ℓʷ)
g₁ * g₂
g₁ ∘ g₂

Compose two BMS elements, in the order in which they are applied: the result acts as g₁ first, and then as g₂, whose parameters are read in the frame that g₁ produces:

\[(Λ₁, α₁)\,(Λ₂, α₂) = \left(Λ₁Λ₂,\; α₁(𝐤) + α₂(Λ̃₁𝐤Λ₁)/κ₁(𝐤)\right),\]

where $κ₁(𝐤) = k⁰/(Λ̃₁𝐤Λ₁)⁰$, and $α₂(Λ̃₁𝐤Λ₁)$ means $α₂$ evaluated at the label that the frame produced by g₁ gives to the ray. The second term is $\mathrm{Ad}(Λ₁)(α₂)$. Applying g₁ and then g₂ with two successive calls to transform! therefore matches applying g₁ * g₂ once, and lorentz(g₁ * g₂) == lorentz(g₁) * lorentz(g₂): multiplying BMS elements extends multiplying their frame rotors. If both elements are instead specified in the original frame, the second becomes the conjugate inv(g₁) * g₂ * g₁ in the frame that g₁ produces, and the composite is g₂ * g₁, as for rotations about fixed axes. See Frames and Components.

Because the functor of an element maps new coordinates to old ones, (g₁ * g₂)(t′, k̂′) ≈ g₁(g₂(t′, k̂′)...), which is Julia's rule for ∘; so g₁ ∘ g₂ == g₁ * g₂. "First" refers to the changes of frame: as maps on coordinates, g₂'s is evaluated first.

Because κ₁ and the new label, read from Λ̃₁𝐤Λ₁, are realized on the labeled celestial sphere, the composed supertranslation depends on the labeling — which each element includes as its I type parameter (see Representations of the supertranslation). The inputs may use any mix of conventions (A, I): each convention the two inputs share is kept for the result, and each convention on which they disagree is resolved by converting both inputs — exactly — to the default (+1). c_α does not otherwise enter the group law.

The composed supertranslation is computed pointwise on a spherical grid of bandwidth ℓʷ, the Leja points of SphericalFunctions' SSHTMatrix, and then re-expanded in spherical harmonics, keeping modes up to ℓₘₐₓ. The default is ℓₘₐₓ = max(ℓ₂ + 1, ℓ₁), where ℓᵢ are the two inputs' resolutions: the term α₁ keeps its own bandwidth, while α₂/κ₁ gains one — the factor 1/κ₁ is exactly band-limited to ℓ ≤ 1, so the product has bandwidth ℓ₂+1. ℓʷ defaults to max(2ℓₘₐₓ + 1, ℓ₂ + 1, ℓ₁).

Band limits

The factor 1/κ₁ is exactly band-limited to ℓ ≤ 1, and for pure rotations α₂ at the new labels has the same bandwidth as α₂ — so when Λ₁ involves no boost, the result is exact (up to roundoff) whenever ℓʷ ≥ max(ℓ₁, ℓ₂), which the defaults guarantee, and a smaller ℓʷ throws an ArgumentError. When Λ₁ involves a boost, however, α₂ at the new labels has unbounded bandwidth (with an exponentially decaying tail), so the result is convergent in ℓʷ rather than exact, and the modes above ℓₘₐₓ are simply discarded. For large rapidities, increase ℓʷ (and possibly ℓₘₐₓ).

Three cases short-circuit the grid entirely and are exact: when α₂ = 0 (so the result is just (Λ₁Λ₂, α₁)); when Λ₁ = ±1 (so κ₁ ≡ 1 and the supertranslations simply add); and when Λ₁ is a pure rotation Q₁ (so κ₁ ≡ 1 and α₂ at the new labels is the band-limit-preserving rigid rotation of α₂'s modes by Q₁, computed with Wigner's $𝔇$ matrices via rotate_modes).

Scri.compute_t′ — Function
compute_t′(t, αₚ, Rₚ, v⃗, ℐ=1)

Compute the new time samples t′ corresponding to the input time samples t after a BMS transformation with supertranslation αₚ and boost velocity v⃗. The Rₚ describe the locations of the pixels. The null-infinity sign ℐ = ±1 enters the conformal factor as 1/κ = γ(1 - ℐ v⃗⋅k̂) (+1 for $ℐ⁺$, -1 for $ℐ⁻$).

The objective is to create a new time grid that has the same number of samples as t and has roughly the same spacing, while accounting for the fact that some parts of the cylinder (the subset of ℐ⁺) on which we have data will need to be dropped because the new slices at the ends will be "tilted", and thus won't have a complete sphere of data on which to compute modes.

The result is a simple rescaling:

scale = (t′ₘₐₓ - t′ₘᵢₙ) / (tₘₐₓ - tₘᵢₙ)
t′ = @. t′ₘᵢₙ + scale * (t - tₘᵢₙ)

Scri.compute_t′ — Method
compute_t′(t, β, δt)

Construct a single output time grid t′ that is guaranteed to consist of complete slices for every BMS transformation whose boost speed is at most β and whose supertranslation satisfies |α(k̂)| ≤ δt in every direction k̂ — regardless of the boost direction, the frame rotation, and the choice of ℐ = ±1.

This is the natural choice for the t′ keyword of transform! in an optimization loop over BMS parameters, where the grid must remain valid at every parameter value the optimizer tries, and where differentiation with ForwardDiff requires the grid to be held fixed. Estimate an upper bound β on the boost speed and an upper bound δt on the magnitude of the supertranslation (including any time translation) that the optimizer may reach, and use the resulting grid for every evaluation.

The grid is built exactly as in the exact-transformation method — an affine rescaling of t onto the worst-case span of compute_t′_bounds. Because the span is a worst case, it is generally smaller than the exact span for any particular transformation.

Scri.transform! — Method
transform!(data, t, v⃗, R, αᵢₙ, dc; t′=nothing, ℓₘₐₓ₀=nothing, plan=nothing)

Transform the mode weights in data — sampled at times t — from the rest frame to the BMS-transformed frame. The BMS transformation is specified by the boost velocity v⃗, the overall rotation R, the supertranslation αᵢₙ, and the DataComponents descriptor dc. The transformation is performed in-place, modifying the input data array.

The complex data array is expected to have dimensions (Nᵐ, Nᵗ, Nᵈ), where Nᵐ is the number of modes, Nᵗ is the number of time samples, and Nᵈ is the number of data components (e.g., strain and/or Newman-Penrose Weyl components). The modes are expected to be ordered by increasing ℓ, then by increasing m within each ℓ. For data with spin weight $s ≠ 0$, the modes with $ℓ < |s|$ are expected to be present, but will be ignored. The maximum ℓ value is determined by the size of the first dimension of data as ℓₘₐₓ = √Nᵐ - 1. The array must have complex type, with the underlying real type being at least as wide as the types of the other inputs.

The t array is expected to have length Nᵗ, matching the second dimension of data. The v⃗ and R inputs are expected to be of types QuatVec and Rotor; other methods also accept plain vectors, tuples, and, for R, quaternions. A velocity must have three components. A rotation given as three components is read as a rotation vector, and four as a rotor; see rotor_argument.

The new frame is obtained from the old one by first rotating its legs by R and then boosting them with velocity v⃗, with both R and v⃗ given in the old frame's components. Specifically, the new observer moves with velocity v⃗ relative to the old one. The basis tetrad is $𝐞'_μ = Λ\,𝐞_μ\,Λ̃$, where the frame rotor is Λ = Boost(v⃗) * R, so its time leg is $γ(𝐭 + v⃗)$. For example, R = Rotor(√2, 0, 0, √2) puts the new $x$ axis along the old $y$ axis, so the event with old coordinates $(t, x, y, z) = (0, 1, 0, 0)$ has new coordinates $(0, 0, -1, 0)$. The velocity v⃗ and the rotation R mean the same thing at $ℐ⁺$ and at $ℐ⁻$. Under a pure rotation, the mode weights of each field become $𝔇(R^{-1})\,f$, which is the frame-rotation law of SphericalFunctions.jl. If this function is called twice, the second call's v⃗ and R are interpreted in the frame resulting from the first transformation, and the result agrees with a single call using g₁ * g₂, where g₁ and g₂ are the BMS elements built from the two calls' parameters; see compose. The conventions are set out on the page Frames and Components.

The αᵢₙ array must be a complex vector, and must be ordered as described above for the final dimension of data, though it may have a smaller ℓₘₐₓ. (A larger ℓₘₐₓ is not allowed, because the result would have higher angular dependence than data, which is not possible since we are transforming data in-place.) This array is expected to represent a supertranslation in the rest frame, which is a real-valued function (with spin weight 0) on the sphere. The reality condition is that the mode weights satisfy $α_{ℓ,-m} = (-1)^m ᾱ_{ℓ,m}$. This function will automatically impose this condition by averaging each mode with its complex-conjugate partner. This is done in a copy of the array for simplicity, rather than being done in place.

The dc argument is a DataComponents value specifying which field components are stored in data, in the order they appear along its third dimension. Because of the hierarchical nature of the BMS transformation, any Weyl component $ψᵢ$ must be accompanied by all higher-index components $ψⱼ$ for $j > i$. Note that DataComponents includes a sign indicating whether data represents data on $ℐ⁺$ if ℐ = +1 or $ℐ⁻$ if ℐ = -1.

The dc argument also contains the Conventions the data are expressed in, and the transformation laws applied are the ones native to that convention — see the "Convention dependence" section of the "BMS Action on Fields" documentation page. With the default conventions (SXS) every factor is the identity and compiles away.

The optional keyword t′ supplies the output time grid explicitly, instead of the default grid constructed by compute_t′. It must be a real vector of the same length as t, strictly increasing, and must lie within the range for which every pixel of the sphere maps into the span of t (as validated by validate_t′; an out-of-range grid throws an ArgumentError). This is chiefly useful in optimization loops over BMS parameters, where a fixed output grid makes the results directly comparable across iterations.

The optional keyword ℓₘₐₓ₀ declares the input band limit: a promise that every mode with $ℓ > ℓₘₐₓ₀$ in data is exactly zero (as when band-limited data have been zero-padded to a larger array, per the pad-first workflow of Choosing $ℓ_\mathrm{max}$). The first (synthesis) stage then processes only the nonzero modes, reducing its cost by roughly the factor (ℓₘₐₓ₀+1)²/Nᵐ. The promise is verified, and an ArgumentError is thrown if any declared-zero mode is nonzero.

The optional keyword plan supplies a TransformPlan for the band limit, precision, and spin weights of data, so that the grid and its analysis factorizations, which depend on no BMS parameter, are not rebuilt on every call.

Returns (data, t′), where t′ is the output time grid (the supplied one, if given).

The transformation is differentiable end-to-end with ForwardDiff with respect to the BMS parameters, provided the output grid is held fixed with t′; see the Automatic Differentiation documentation page. Note, however, that differentiating through transform! requires a dual-typed copy of the entire data array; when the goal is to optimize the BMS parameters against a fixed target waveform, the memory-lean transform_objective computes the L² objective directly, leaving data primal and untouched.

Scri.transform_objective — Method
transform_objective(data, t, v⃗, R, αᵢₙ, dc, plan; ℓₘₐₓ₀=nothing)

Compute the objective of the ObjectivePlan plan, the weighted $L²$ difference between the BMS-transformed data and the plan's target, as a single real scalar:

\[Φ = \frac{1}{𝒩} ∑_j w_j ∑_i v_i ∑_k u_k \left| μ^{ki}_{j} - c^{ki}_{j} \right|^2,\]

where $μ^{ki}_{j}$ is the transformed waveform at the plan's pixel j, output time plan.t′[i], and component k, and the target $c$, the weights $w$, $v$, and $u$, and the normalization $𝒩$ are the plan's. With the plan's default grid and time weights, $Φ$ is a quadrature of the integral of $|μ - c|²$ over the sphere and the time window, exact over the sphere for band-limited fields. This is the natural objective for optimizing the BMS parameters (v⃗, R, αᵢₙ) to align data with a target waveform, and it is designed for use with ForwardDiff: see the Automatic Differentiation documentation page for a complete recipe.

The data, t, v⃗, R, αᵢₙ, dc, and ℓₘₐₓ₀ arguments are exactly as in transform! — except that data is never modified, and its element type need not be widened to match the parameter types. In particular, when v⃗, R, or αᵢₙ hold ForwardDiff dual numbers, data stays primal and is simply read; no dual-typed copy of the (typically very large) data array is ever made, no dual-typed synthesis matrices for the whole grid are built, and the analysis stage of transform! is skipped entirely. The pixels are synthesized a block at a time, each block by one matrix product per component, and dual numbers are confined to the pixels' geometry, the harmonics and time series of one block, and a few buffers of size O(Nᵈ × Nᵗ) for each thread. The block's harmonics and time series take no more memory than data itself, or 128 MiB if that is larger, except that a block always holds at least four pixels for each thread. So the memory overhead of differentiation is modest, and data can be reused across optimizer iterations without copying. A BMS-valued transformation may be passed in place of (v⃗, R, αᵢₙ), and v⃗ and R may also be plain vectors or tuples, such as slices of an optimizer's parameter vector. A velocity must have three components. A rotation given as three components is read as a rotation vector, and four as a rotor; see rotor_argument.

The plan's output grid t′ is held fixed across parameter values, which is what makes objective values (and derivatives) comparable across optimizer iterations. It must remain within the valid span (validate_t′) at every parameter value; build it with compute_t′(t, β, δt) for the largest boost and supertranslation the optimizer may try. dc must have the same components as the plan, and with the plan's default grid the data's band limit (or ℓₘₐₓ₀, if given) must not exceed the target's.

Two fine points. First, the spline-interval selection inside the interpolation is discontinuous on a measure-zero set of parameter values (where a transformed time t′[i] κ⁻¹ + αₚ crosses a knot of t); the objective itself is continuous there, and derivatives are unaffected away from those isolated points. Second, the result is deterministic: each pixel's share is computed on its own and the shares are summed in pixel order, so for a fixed number of threads, repeated calls with identical inputs return bitwise-identical values.

Returns a real scalar of the common promoted type of the inputs — a ForwardDiff dual when the parameters carry duals.

Scri.CubicSplineCache — Method
CubicSplineCache(t)

Precompute the Thomas LU factorization of the natural-cubic-spline tridiagonal system for knot vector t. t must be strictly increasing with at least 4 elements. The cache holds floating-point numbers even when t holds integers.

Natural spline system

For N knots, the N−2 interior second derivatives d̈[2..N-1] satisfy the symmetric tridiagonal system

h[j-1]*d̈[j-1] + 2(h[j-1]+h[j])*d̈[j] + h[j]*d̈[j+1] = rₖ[j]

with d̈[1]=d̈[N]=0 (natural boundary conditions) and

rₖ[j] = 6*( (d[j+1]−d[j])/h[j] − (d[j]−d[j-1])/h[j-1] ).

Denoting the system Ad̈ₖ = rₖ, the Thomas LU factorization gives

A = LU,  L unit lower bidiagonal with factors lᵢ,
          U upper bidiagonal with diagonal uᵢ and super-diagonal sᵢ = h[i+1].

Thomas forward sweep

With the cache built, the forward sweep for a new data vector d is

z[2] = r[2] * u⁻¹[1]
z[j] = ( r[j] − h[j-1] * z[j-1] ) * u⁻¹[j-1]   for j = 3..N-1

and the backward sweep recovers d̈ from z:

d̈[N-1] = z[N-1]
d̈[j]   = z[j] − l[j-1] * d̈[j+1]                for j = N-2:-1:2

Evaluation

On interval [t[j], t[j+1]] at offset τ = t_query − t[j]:

c = (d̈[j+1]−d̈[j]) * h⁻¹[j] / 6
b = d̈[j] / 2
a = h⁻¹[j]*(d[j+1]−d[j]) − h[j]/6*(2d̈[j]+d̈[j+1])
S = d[j] + τ*(a + τ*(b + τ*c))

Scri.MinusOne — Type
One
MinusOne

Singleton types representing the numbers $+1$ and $-1$ at the type level.

Their whole purpose is to make a sign that is fixed by a choice of convention disappear from the generated code. Because the value is encoded in the type, multiplication is resolved at compile time: One() * x returns x itself (the very same object) and MinusOne() * x returns -x, so a convention factor of $±1$ costs nothing (at most a negation) rather than a runtime multiply. Products of these singletons stay singletons (MinusOne() * MinusOne() === One()), so a chain like $c_s c_ψ c_R$ collapses to a single One/MinusOne before it ever touches field data.

They deliberately do not subtype Number. A $±1$ newtype that did would have to define *(::One, ::Number) and convert(::Type{<:Number}, ::One), which then clash — irreconcilably, across dozens of ambiguities — with every other package that adds its own Number subtype (quaternions, static integers, extended-precision floats, …). Staying outside the Number hierarchy means those downstream methods simply never apply to a singleton, so the identity and negation methods below win cleanly. The small numeric interface they do need (==, ≈, ^, conversion, …) is supplied here by concrete dispatch.

These are internal helpers used to store the sign fields of Conventions; values are normalized to them by the Conventions constructor, so user code rarely names them directly.

Base.inv — Method
inv(g::BMS; ℓₘₐₓ, ℓʷ)

The inverse BMS element,

\[(Λ, α)^{-1} = (Λ̃, 0)\,(1, -α) = \left(Λ̃,\; -α(Λ𝐤Λ̃) / κ(Λ̃, 𝐤)\right),\]

with $κ(Λ̃, 𝐤) = k⁰/(Λ𝐤Λ̃)⁰$; that is, $(Λ̃, -\mathrm{Ad}(Λ̃)(α))$. It is computed through compose. The result inherits g's conventions (A, I), and the null-infinity representation I governs the geometry internally. compose's band-limit caveats (and ℓₘₐₓ/ℓʷ keywords) apply here too: the inverse of an element whose Lorentz part involves a boost is exact only in the limit of large ℓʷ and ℓₘₐₓ. The Lorentz part inv(Λ) is the exact GA reverse.

The default ℓₘₐₓ is one more than that of g, which is also the band limit that compose gives inv(g) * g by default. The two truncations then coincide, so inv(g) * g, which applies inv(g) first, is the identity to roundoff. The other order, g * inv(g), truncates differently and is exact only in the limit.

Scri.aberration — Method
aberration(R′ₚᵢ, Λℐ)

Return the point frame, in the old frame's components, of the ray that the new frame labels with the pixel rotor R′ₚᵢ. The second argument is the frame rotor Λ = Boost(v⃗) * R of the change of frame, which already folds in the boost velocity $v⃗$ and the frame rotation $R$; see Frames and Components. At $ℐ⁻$ the caller should pass its parity conjugate Boost(-v⃗) * R instead, as described below, which is why the argument is named Λℐ.

The result is the $K$ factor of the Iwasawa $KAN$ decomposition of Λℐ * R′ₚᵢ. It points along the same null direction in the old frame as R′ₚᵢ does in the new one, and it includes the tangent-frame orientation (spin phase), which is exactly the information a spin-weighted field needs. The $A$ factor is accounted for by the conformal factor $κ$, and the $N$ factor by component mixing, so only $K$ is computed here, which is cheaper than the full KAN computation. Projecting with the idempotent $u₊ = (1+𝐭𝐳)/2$ gives $ℂℜ(Λ_ℐ𝐑'_p u₊) = ½e^{φₐ/2}𝐑_K$, which normalizes to $𝐑_K$. See the "Reversing the order" section of The Lorentz Group page for why $K$ is the relevant object, and the Quaternionic documentation for the extraction.

The choice of $ℐ⁺$ versus $ℐ⁻$ enters only implicitly through the boost velocity in the second argument, which the caller is assumed to provide correctly. The $u₊$ extraction is tied to the null vector $ℓ ∝ (1, +k̂)$ where the pixel rotor takes $𝐳 → k̂$, which matches the $ℐ⁺$ labeling directly. At $ℐ⁻$ the labeling is antipodal — pixel $k̂$ labels the null vector $(1, −k̂)$ — and conjugating by spatial parity turns $B(v⃗)$ acting on $(1, −k̂)$ into $B(−v⃗)$ acting on $(1, +k̂)$, while leaving the parity-invariant rotation factor $K$ unchanged. So both cases use the same extraction, with Boost(ℐ * v⃗) * R as the second argument: the frame rotor $Λ$ at $ℐ⁺$, and its parity conjugate ℂconj(Λ) at $ℐ⁻$.

This computation is purely algebraic — with no transcendental functions or branches — and globally nonsingular, since $ℂℜ(Λ_ℐ𝐑'_p u₊)$ has norm $½e^{φₐ/2} > 0$ everywhere. An independent derivation via explicit angles on the sphere, used as the test oracle, is described on the Aberration of Gravitational Waves documentation page.

Scri.compute_t′_bounds — Method

Return the extreme values (t′ₘᵢₙ, t′ₘₐₓ) of a transformed time grid that remain valid for every BMS transformation whose boost speed is at most β and whose supertranslation satisfies |α(k̂)| ≤ δt in every direction k̂. A returned pair that does not satisfy t′ₘᵢₙ < t′ₘₐₓ means that some admissible transformation may leave no complete slice.

Scri.compute_ðt′╱2κ — Function
compute_ðt′╱2κ(Rₚ, v⃗, αₚ, ðαₚ, ℐ=1)

Compute the null-rotation parameter $ðt'/2κ$ (where $t$ can represent either $u$ or $v$, depending on ℐ) on the boosted grid Rₚ, returned as a 2 × length(Rₚ) matrix split into a part independent of the time t (row 1) and the coefficient of t (row 2):

ðt′╱2κ(t)[i] = ðt′╱2κ[1, i] + t * ðt′╱2κ[2, i].

The time-coefficient is just $ðκ/2κ$, which has the closed form below in terms of $λ = R̃ᵢ v⃗ Rᵢ$ (the rest-frame components of the boost velocity at pixel i); the time-independent part folds in the $c_α$-corrected supertranslation αₚ and its eth-derivative ðαₚ:

ðt′╱2κ[2, i] = (λˣ + im * λʸ) / 2(λᶻ - ℐ),
ðt′╱2κ[1, i] = -(ðt′╱2κ[2, i] * αₚ[i] + ðαₚ[i] / 2).

See the documentation page "Computing $ðt'/κ$" for the derivation. Note in particular that the boost × supertranslation cross term $ðt'╱2κ[2, i]·αₚ[i]$ enters with a minus sign.

The denominator $λᶻ - ℐ$ is the difference that sets $1/κ$, since $λᶻ = v⃗⋅k̂$, and it loses accuracy in the same way on the red-shifted side of a fast boost: the relative error of $ðκ/2κ$ there is about $ε/(1 - β)$ for the speed $β = |v⃗|$ and the machine epsilon $ε$, which is negligible at the speeds of recoiling black holes.

Scri.dyad_factor — Method
dyad_factor(c::Conventions)

The dyad scaling $c_l c_m$ — the only convention combination that enters the homogeneous (peeling-tower) transformation laws. Scri.gauss_legendre — Method
gauss_legendre(n, T=Float64)

Return the nodes x (ascending) and weights w of the n-point Gauss–Legendre rule on $[-1, 1]$, which integrates every polynomial of degree at most $2n-1$ exactly: $∫_{-1}^{1} p(x)\, dx = ∑_i w_i\, p(x_i)$.

The nodes are found by Newton's method on the Legendre polynomial $P_n$, evaluated by its three-term recurrence, starting from Tricomi's approximation $\cos(π(4i-1)/(4n+2))$. This works in any floating-point type T, such as Double64 or BigFloat, where an eigenvalue method would need a generic eigensolver. The weights are $2/((1-x_i^2) P_n'(x_i)^2)$; for the outer nodes, $1 - x_i^2$ and $P_n'$ are computed from $1 - |x_i|$ as in one_minus_node. Computed directly from $x_i$, they would have a relative error of about $ε/(1 - |x_i|)$, as large as $500ε$ at $n = 100$; computed this way, they are as accurate as the weights near the equator.

Scri.lambda_factor — Method
lambda_factor(c::Conventions)

Scri.one_minus_node — Method
one_minus_node(n, z)

Return $1 - z$ for a node $z ≥ 0$ of the n-point Gauss–Legendre rule, to full relative accuracy. A node near $z = 1$ is known only to an absolute accuracy of about $ε$, so the difference $1 - z$ there has a relative error of about $ε/(1 - z)$, which is $ε/θ^2$ in terms of the colatitude $θ$ of the node. As Bogaert [43] points out, the nodes cluster quadratically near $z = ±1$, so they are better computed in $θ$, or in $1 - z$, than in $z$ itself. For $z ≥ 1/2$, $v = 1 - z$ is therefore found afresh by Newton's method in $v$, starting from $1 - z$. The Legendre polynomial is evaluated there by Reinsch's form of the recurrence, which works with the differences $d_k = P_k - P_{k-1}$,

\[d_k = \frac{(k-1)\, d_{k-1} - (2k-1)\, v\, P_{k-1}}{k}, \qquad P_k = P_{k-1} + d_k,\]

starting from $P_0 = 1$ and $d_1 = -v$, so that nothing is lost to cancellation near $z = 1$. The derivative follows from the identity of legendre_and_derivative, as $dP_n/dv = n (d_n - v P_n)/(v (2 - v))$. For $z < 1/2$, $1 - z$ is already accurate and is returned as it is.

Scri.sphere_quadrature — Method
sphere_quadrature(ℓₘₐₓ, T=Float64)

Return rotors R and weights w of a quadrature on the sphere that integrates exactly the product of any two fields of the same spin weight that are band-limited to $ℓ ≤ ℓₘₐₓ$:

\[∫ f\, \bar{g}\, dΩ = ∑_i w_i\, f(R_i)\, \bar{g}(R_i) = ∑_{ℓ,m} f_{ℓ,m}\, \bar{g}_{ℓ,m}.\]

The grid is the product of $ℓₘₐₓ+1$ Gauss–Legendre nodes in $\cos θ$, from gauss_legendre, and $2ℓₘₐₓ+1$ equally spaced values of $φ$, about twice as many points as there are modes. That suffices because such a product is a polynomial of degree at most $2ℓₘₐₓ$ in $\cos θ$ times $e^{ikφ}$ with $|k| ≤ 2ℓₘₐₓ$. The rotors are those of from_spherical_coordinates(θ, φ); no node lies at a pole.

The rotors are formed from $\sin(θ/2)$ and $\cos(θ/2)$, which are $\sqrt{v/2}$ and $\sqrt{1 - v/2}$ for a node with $\cos θ = 1 - v$, rather than from $θ = \arccos x$. Near a pole, $\arccos x$ has a relative error of about $ε/θ^2$, and the small component of a rotor there would inherit it: about $26ε$ at $ℓₘₐₓ = 32$ and $24000ε$ at $ℓₘₐₓ = 1000$. With $v$ from one_minus_node, and the roles of the two reversed at the southern nodes, the relative error is about $ε$ at every node. The same holds in azimuth, where $\sin(φ/2)$ and $\cos(φ/2)$ are formed with sinpi from exact ratios of integers no larger than $1/2$, because either of them formed from a rounded $φ$ would lose digits where it is small.

validate_transform_inputs(data, t, v⃗, R, αᵢₙ, dc, ℓₘₐₓ₀)

Scri.validate_t′ — Function
validate_t′(t′, t, αₚ, Rₚ, v⃗, ℐ=1)

Check that a user-supplied output time grid t′ is usable by transform! or transform_objective: it must be nonempty, finite, strictly increasing, and lie within the pixel-wise bounds of compute_t′_bounds (up to a small roundoff allowance), so that no pixel ever requires extrapolation beyond the input time span. Scri.v⃗dotk̂ — Method
v⃗dotk̂(Rₚᵢ, vˣ, vʸ, vᶻ)

Compute $v⃗ ⋅ k̂$ for the direction $k̂ = Rₚᵢ 𝐤 R̃ₚᵢ$ singled out by the pixel rotor Rₚᵢ — the third column of the rotation matrix of Rₚᵢ, contracted with the boost velocity components. This is the angular dependence entering the inverse conformal factor $1/κ = γ(1 - ℐ v⃗⋅k̂)$. Generic over the component types, so Rₚᵢ and the velocity may carry dual numbers.

The difference $1 - ℐ v⃗⋅k̂$ loses accuracy on the red-shifted side of a fast boost, where $ℐ v⃗⋅k̂$ approaches the speed $β = |v⃗|$: the relative error of $1/κ$ there is about $ε/(1 - β)$ for the machine epsilon $ε$, which is $2.5 × 10^{-12}$ at $β = 0.9999$ and $8 × 10^{-9}$ at $β = 1 - 10^{-8}$ in Float64, and is negligible at the speeds of recoiling black holes.
